## The decision the session opens with: land first, or test from the worktree

The point of new stories is to see the migrated harness on real agents,
and most of what the fakes could not exercise (real `claude` JSON, real
`codex` JSONL, the 30-minute timeout, memory, the bot's `/status`) is only
seen through the queue. So the recommendation is to **land the branch
before promoting a story**, as the fleet-develop skill has it:

```bash
systemctl --user is-active fleet-queue.service fleet-bot.service   # both must say inactive
cd ~/work/fleet && git merge --ff-only ts-classifier               # main = 1f83cb1
bash test-lib.sh                                                    # in the live checkout, once; 710
bash status.sh khaita && bash launch.sh khaita --reap               # smoke: exit 0, nothing changes
```

Nothing else is needed after the fast-forward: no `npm ci` (nothing under
`ts/` needs `node_modules` at run time), node v24.20.0 is already on the
units' PATH (`.nvmrc`), the unit files are unchanged.

If the human prefers to try the launcher from the worktree first, the
hand-run form still holds — never as a child of the session:

```bash
cd ~/work/fleet-wt-ts-classifier
setsid nohup bash -c 'bash launch.sh khaita 0NN; echo "exit=$?"' > /tmp/launch-0NN.log 2>&1 < /dev/null &
```

Two things differ from a queue run: the worktree has no `.env.fleet`, so
the `needs_human`/`blocked` notifications go nowhere (the notifier never
fails, by design — `FLEET_NOTIFY_CMD` can be pointed at the live
`telegram.sh`); and the queue's merge on PASS does not happen. The
worktree's `repos/khaita.env` is the same tracked file as the live one.

## What to watch on the first real story

The fakes proved the machinery; these are the places where a real agent
could still surprise, each with where to look:

1. **The builder's output shape.** `round-1/builder.json` should be the
   CLI's one object (`is_error`, `result`, cost and duration fields) and
   `builder.md` the `result` text. A non-string `result` would be printed
   as pretty JSON — that is what jq did, but it has never been seen live.
   The log line `builder output was not JSON — first 20 lines` means JSON of
   the wrong shape (see case 111b); non-JSON is silent, as bash had it.
2. **The reviewer's stream.** `reviewer.md` must be prose, `reviewer.stderr`
   the "Reading additional input from stdin..." notice. A line in the
   launcher's log reading `jq: error (at <stdin>:N): Cannot index …` means
   codex printed a JSON value that is not an object — harmless, and worth
   knowing the shape of.
3. **No `unsubstituted in …: {{STORY}}` warning** for a story whose text
   has `&` or `&&`. Before L-28 that line appeared in the queue journal for
   012, 017, 018, 019. A new story that uses `&&` in its ACs is the natural
   probe: `journalctl --user -u fleet-queue | grep unsubstituted` must stay
   empty.
4. **The timeout and the group kill.** `AGENT_TIMEOUT=1800` comes from the
   unit. If an agent is killed, the log says `exceeded AGENT_TIMEOUT
   (1800s)`, the story goes to `needs_human`, and
   `procs_in_worktree ../wt-<id>` must be empty afterwards — the launcher
   kills the whole process group where bash's `timeout` did the same.
5. **Memory.** `MemoryHigh=2500M` on the queue unit; the launcher is now a
   node process alongside claude, codex and vitest. `systemctl --user status
   fleet-queue` during a round shows the cgroup's memory; the box has 3.9 GB.
6. **The Machine block's `timing:` line** — integer seconds, from the
   launcher's own clock rather than bash's `SECONDS`; expect the same
   magnitudes as before (`.review/<id>.md`).
7. **Status and the bot under the units' locale.** The units set no `LANG`;
   the TypeScript renders UTF-8 widths regardless (a seam-3 non-parity), so
   a title with an em dash now aligns in `/status` where bash's table was
   two columns wide there.
8. **The `.result` files and `test.summary.json`** in `round-N/` — same
   shapes as before; a `{"error": …}` summary means the runner wrote
   nothing usable (see `baseline.test.ts` for the three texts).

If any of these differs from the record in the plan document, that is a
finding: either a non-parity to pin with a test, or a bug. The suite's
fakes should then gain the real shape, as `test/codex` gained the stderr
notice on 17 Sep.
