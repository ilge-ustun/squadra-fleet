# Prompts

Bodies for the builder and reviewer, rendered by `render_prompt()` in
`fleet/render.sh` and sourced by `launch.sh`.

Values are referenced as `{{NAME}}`, never `$NAME`, so these files are inert
text: nothing expands by accident and a prompt file cannot inject shell.

| file | placeholders |
|---|---|
| `rules.md` | `{{STORY_ID}}` |
| `build-round1.md` | `{{STORY_ID}}` `{{RULES}}` |
| `build-round2.md` | `{{STORY_ID}}` `{{RULES}}` `{{REVIEW_TEXT}}` |
| `review.md` | `{{STORY_ID}}` `{{HEAD_SHA}}` `{{BASE_SHA}}` `{{ROUND}}` |

Render `rules.md` first — it contains `{{STORY_ID}}` and is then embedded as
`{{RULES}}` in both build prompts.

## The verdict contract

The last line of `review.md` is parsed in three places that do not reference
each other:

1. `launch.sh` greps `^VERDICT: (PASS|FAIL)[[:space:]]*$` on the reviewer's output
2. it writes `verdict: <value>` — lowercase — into `.review/<id>.md`
3. on restart, `launch.sh` greps `^verdict: (FAIL|UNPARSEABLE)` in that file to
   decide whether the builder resumes from the findings

Change the wording of that line and two other things break silently: a review
that does not match becomes `UNPARSEABLE`, which is treated as not-PASS, and the
builder burns another round for a formatting reason.

`UNPARSEABLE` is generated by the launcher when the output matches neither
value. The reviewer is never told it exists.
