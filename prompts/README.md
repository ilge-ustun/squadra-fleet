# Prompts

Bodies for the story writer, the builder and the reviewer, rendered by
`renderPrompt()` in `ts/src/lib/render.ts` — by the launcher, and by
`fleet write-story`.

Values are referenced as `{{NAME}}`, never `$NAME`, so these files are inert
text: nothing expands by accident and a prompt file cannot inject shell.

| file | placeholders |
|---|---|
| `rules.md` | `{{STORY_ID}}` `{{REPO_RULES}}` `{{CHECK_MUTATION}}` `{{VITEST_CMD}}` `{{BUILD_CMD}}` `{{LINT_CMD}}` `{{E2E_STEP}}` |
| `build-round1.md` | `{{RULES}}` `{{STORY}}` |
| `build-round2.md` | `{{STORY_ID}}` `{{RULES}}` `{{STORY}}` `{{REVIEW_TEXT}}` |
| `build-after-spec.md` | `{{RULES}}` `{{STORY}}` `{{REVIEW_TEXT}}` |
| `review.md` | `{{STORY}}` `{{HEAD_SHA}}` `{{BASE_SHA}}` `{{ROUND}}` `{{VITEST_CMD}}` `{{BUILD_CMD}}` `{{LINT_CMD}}` `{{E2E_STEP}}` `{{BASELINE}}` |
| `write-story.md` | `{{STORY_ID}}` `{{INTENT}}` `{{STORY_BASE}}` |

Render `rules.md` first — it contains `{{STORY_ID}}` and is then embedded as
`{{RULES}}` in every build prompt.

`{{BASELINE}}` is the harness's own baseline at the head under review —
its line, the suite's count and failed names, and where its logs are
(`baselineForReviewer` in `ts/src/lib/baseline.ts`) — so the reviewer does
not spend minutes re-running what the harness already ran (L-39). It is the
last replacement, so nothing in it is substituted, and it is guarded: a
review prompt is never rendered without it.

## The verdict contract

The reviewer's line `VERDICT: PASS|FAIL|SPEC` is **one input** to the
verdict, not the verdict. The rule is `ts/src/lib/verdict.ts`, called by
the launcher (`ts/src/launch.ts`) once per round:

```
machine_pass := baseline green — test, build, lint, run by the harness
             ∧ scope CLEAN — no changed path the story's scope_deny names
             ∧ every **ACn in the story has ≥1 mutation in .review-out/mutations/
             ∧ every mutation is RED when the harness runs it
             ∧ no probe is RED
final        := the reviewer's word, except that PASS becomes FAIL when
                machine_pass is false. SPEC, FAIL and UNPARSEABLE stay as
                they are. Every failing condition is listed on the
                `computed:` line of the round's `### Machine` block,
                whatever the verdict.
```

**The machine can veto, never grant.** Nothing becomes PASS that the reviewer
did not call PASS; a reviewer PASS becomes FAIL when the machine disagrees.

The reviewer's line is parsed in four places that do not reference each
other:

1. `ts/src/lib/verdict.ts` matches `^VERDICT: (PASS|FAIL|SPEC)[[:space:]]*$`
   on the reviewer's text — on **any** line, not only the last, although
   `review.md` asks for the last; PASS wins over FAIL over SPEC when several
   are present. Recorded here rather than tightened; a change needs a
   `test/suite.sh` case first.
2. it writes `verdict: <computed>` — lowercase — as line 3 of `.review/<id>.md`
3. on restart, the launcher matches `^verdict: (FAIL|UNPARSEABLE|SPEC)` there
   to decide whether the builder resumes from the findings
4. on restart, `verdict: UNAVAILABLE` on line 3 (`readReview`) means the
   last review was refused by its provider: the launcher resumes at that
   review, with no builder round, and the queue runs that story first

`UNPARSEABLE` is generated by the launcher when the reviewer's text matches
none of the three values. It is treated as not-PASS. The reviewer is never
told it exists.

`UNAVAILABLE` is the launcher's too, and never computed: its stream showed
the provider refused the call (an `error` or `turn.failed`, no
`turn.completed`), so nobody reviewed. A reviewer that writes
`VERDICT: UNAVAILABLE` is UNPARSEABLE.

`SPEC` means the criterion cannot be satisfied by any implementation — the
story is wrong, not the build. It ends the rounds immediately, is immune to
the machine veto, and goes straight to `needs_human`.

## The reviewer's output contract

Besides its prose, the reviewer writes files under `.review-out/mutations/`
in its checkout: `ACn-<slug>.patch` plus one of `ACn-<slug>.test` (a vitest
selector, one line) or `ACn-<slug>.cmd` (a command, one line). The harness
applies, runs, classifies and restores; the reviewer must leave the tree
otherwise clean or the run stops at `needs_human`. See `review.md`.

Mutation classes: `RED` (a real failure: `numFailedTests > 0`, or non-zero
exit for `.cmd`), `GREEN` (survived — the instrument is absent for that
behaviour), `NO_TESTS` (zero tests collected: the mutation broke compilation;
never counts as RED), `PRE_RED` (the selector was already failing unmutated;
proves nothing), `SELECTOR_INVALID` (the selector collected no tests even
before the mutation — a path that does not exist, a `-t` pattern matching
nothing, or a shell command in a `.test` file), `PATCH_INVALID`,
`NO_SELECTOR`. Only `RED` satisfies the verdict.

## Evidence

```
.review/<id>.md            summary; `verdict:` on line 3; one section per round,
                           each with a ### Machine block before the prose
.review/<id>/round-N/      committed with the status
  baseline/                test.summary.json (trimmed by ts/src/lib/baseline.ts), build.log, lint.log
  mutations/               the reviewer's files, plus a .result per mutation
  reviewer.md              the reviewer's prose, verbatim
  builder.md               the builder's result message
.runs/                     raw vitest JSON and logs — machine-local, gitignored,
                           re-derivable from patch + HEAD SHA
```

Round 2's `{{REVIEW_TEXT}}` is the review file so far — Machine blocks and
prose — the same content a restart reloads from disk. One path.

`test/suite.sh` exercises all of this with fake agents; every case names
the block whose deletion turns it red.
